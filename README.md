# Helium Native Plugin SDK

Helium SDK is a small development kit for building **native plugins** that a compatible Helium host can load. It defines the shared C ABI used to identify a plugin, start and stop it, write host log messages, and discover optional host services. The repository includes a C++ example, a Rust example, package-manifest schema, and tests for the ABI.

This is a plugin interface, not a standalone application or a Minecraft mod loader. A host application must implement ABI v1, provide the services a plugin requests, and decide where plugin packages are installed. The SDK does not install plugins or launch the game.

## What is included

| Path | Purpose |
| --- | --- |
| `include/helium/helium.h` | Public C/C++ plugin ABI |
| `crates/helium-sdk` | Rust definitions matching the plugin ABI |
| `examples/cpp-minimal` | Minimal C++17 shared-library plugin |
| `examples/rust-minimal` | Minimal Rust `cdylib` plugin |
| `manifest/helium-plugin.schema.json` | JSON Schema for plugin package manifests |
| `tests` | C header and native plugin contract checks |
| `docs/ABI.md` | Detailed ABI, lifecycle, event, and compatibility guide |

The event bus is maintained in a separate **Dinit** repository. This SDK consumes Dinit's Rust crate and public C header; it does not include or copy the event-bus implementation.

## Requirements and checkout layout

For native C/C++ builds, install CMake 3.20 or later, a C11 compiler, and a C++17 compiler. For Rust builds, install stable Rust and Cargo. Python 3 is needed for the Rust example's packaging script.

Check out the SDK and Dinit next to one another:

```text
workspace/
├── Dinit/
└── Helium-SDK-v1-repo/
```

The native CMake build reads `../Dinit/include`. The Rust workspace refers to the Dinit crate at `../../../Dinit` from `crates/helium-sdk`. Keep this relative layout when building the examples.

## Build and test

### C and C++

From the SDK directory, run:

```sh
./scripts/test-native.sh
```

This configures CMake, builds the C++ plugin and ABI smoke tests, runs CTest, and checks that the generated C++ package contains a valid manifest and library. To choose a different build directory, pass it as the first argument:

```sh
./scripts/test-native.sh /path/to/build
```

The equivalent manual steps are:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

The C++ example package is generated at:

```text
build/package/dev.helium.cpp-example/
├── helium-plugin.json
└── <platform-specific shared library>
```

### Rust

Run the Rust tests and build the example package with:

```sh
cargo fmt -p helium-sdk -p helium-example-rust-plugin -- --check
cargo test --workspace
python3 scripts/package-rust-example.py
```

The packaging script builds the Rust plugin in release mode and places the library and `helium-plugin.json` in:

```text
build/package/dev.helium.rust-example/
```

## Using an example package

A plugin package contains a manifest and the native library named by that manifest. The manifest describes the plugin to the host; the library exports the ABI entry point. For example:

```json
{
  "id": "dev.helium.cpp-example",
  "name": "Helium C++ Example",
  "version": "1.0.0",
  "api_version": 1,
  "library": "libhelium_cpp_example.so"
}
```

The library filename is platform-specific. Use the file generated by the build rather than copying the example filename above blindly. The `id` must be a dot-separated identifier containing letters, numbers, underscores, or hyphens; the `library` value is a filename, not a path. The full constraints are in `manifest/helium-plugin.schema.json`.

To try a package, use a host that explicitly supports this ABI version and follow that host's installation instructions. The SDK itself does not define a universal plugin folder or a runtime loader.

## How a plugin works

1. The host validates the package manifest and loads the shared library.
2. The host looks up `helium_plugin_query_v1` and requests ABI version 1.
3. The plugin returns a pointer to its static descriptor, or null if it does not support the requested ABI.
4. The host calls `on_load`, giving the plugin a host table for logging and service discovery.
5. The plugin can request optional, versioned services, such as Dinit's event service.
6. When the plugin is stopped, the host removes its event subscriptions, waits for callbacks already in progress, calls `on_unload`, and unloads the library.

The descriptor, string encoding, callback rules, error values, event names, and ownership guarantees are described in [`docs/ABI.md`](docs/ABI.md). Native plugins run inside the host process with the host's privileges and are **not sandboxed**. Only load libraries you trust.

## What ABI v1 provides—and does not provide

ABI v1 includes plugin metadata, load and unload callbacks, host logging, and versioned service discovery. Dinit provides a typed Rust event bus and a C ABI service table for client lifecycle, Helium module-tick, and render-frame events.

`TICK_PRE` and `TICK_POST` wrap Helium's module tick as observed by the client's frame hook; they are not Minecraft's vanilla tick-injection points. `RENDER_FRAME` runs after the client's rotation update and before overlay rendering. Cancelling it skips that overlay draw, not the rotation update.

The separate Helium Client project owns runtime integration and plugin loading. This SDK does not inject into Minecraft and does not patch, build, or depend on Helium Client. Minecraft handles, general-purpose rendering services, packet events, and C# bindings are not provided by this SDK.

ABI versioning is independent of Minecraft versions and mappings. A host must support ABI v1 and the services a plugin needs; a stable ABI alone does not guarantee support for a particular game version, platform, or capability.
